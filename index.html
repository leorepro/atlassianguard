導入背景

雲端協作平台，往往是資料治理最容易被略過的一段

多數組織已在端點防護、雲端存取安全代理與資安事件管理平台上投入相當資源，但 Jira 議題附件與 Confluence 頁面中的合約條款、客戶名單與系統憑證，通常未被納入同一套治理框架。常見的風險缺口集中於三類日常性疏漏，而非外部入侵：離職人員的存取權未即時解除、內部頁面被設定為公開連結、以及 AI 助理檢索到原本不應納入索引的內容。

Atlassian Guard 針對的正是這一段落差。Standard 建立身分與存取的邊界，Premium 則延伸至資料本身：內容於寫入當下即完成掃描與分級，異常行為在數分鐘內轉為告警，並提供可直接執行的修復建議。

三個防護層次

隨組織規模擴充的防護能力

Atlassian Cloud 的資安能力分為三層，後者疊加於前者之上。釐清目前所處的層次，是選版判斷的起點。

Layer 1

Atlassian 平台

預設即具備

每個 Atlassian Cloud 方案均內含的基本身分與資料控制，包含站台層級的權限管理與產品自身的安全設定。無須額外訂閱。

Layer 2

Guard Standard

組織層級的可視性與控制

將控制範圍由單一站台提升至整個組織的所有帳號：強制單一登入與兩步驟驗證、SCIM 自動佈建、API token 管控，以及跨產品的稽核記錄。

Layer 3

Guard Premium

進階防護與威脅偵測

由存取層延伸至資料本身：資料分級與自動分類、內容掃描、異常行為偵測，以及告警調查與修復動作。適用於持有高價值資料的組織。

身分與存取

Guard 與身分識別提供者如何協作

Guard 不自行保存密碼，也不另建帳號目錄：登入交給公司的 Identity provider 驗證，帳號與群組則由 IdP 單向同步進 Atlassian 組織。圖一與圖二分別說明「登入的那一刻」與「帳號從到職到離職的生命週期」。

登入時：以公司 IdP 進行 SSO

使用者以公司的 Identity provider（Okta、Microsoft Entra ID、Google Workspace）登入，密碼原則與多因素驗證要求由 IdP 統一控管，Atlassian 端不另存密碼。首次登入時自動建立 Atlassian 帳戶，之後每次登入皆套用 IdP 當下的驗證設定。

受管帳號

Guard 如何把帳號收進組織的控制範圍

Atlassian 帳號隸屬於人，而非任何單一產品。Guard 先由組織驗證其擁有的電子郵件網域（Claimed domain），再把使用該網域的帳號納為受管帳號（Managed accounts）；驗證政策、密碼原則與 API token 管控隨之套用在帳號本身，而非逐站台設定。圖三以 Acme Global 為例：兩個已驗證網域的帳號進入納管，供應商網域的帳號留在範圍之外。

產品方案與 Guard 的分工

已經有 Jira，為什麼還需要 Guard？

兩者的作用範圍不同。Jira 與 Confluence 方案中的安全控制，範圍為單一站台與單一產品，處理的是應用程式的存取條件；Atlassian Guard 的範圍為整個組織的所有帳號與所有 Atlassian 產品，處理的是身分與資料本身。兩者為並行的訂閱，升級 Jira Premium 不會取得 Guard 的任何能力，反之亦然。

為何產品方案無法取代 Guard：Jira Premium 的 IP 許可清單僅於站台層級生效，依官方文件不涵蓋 admin.atlassian.com 與帳號管理的 REST API。更根本的是，Atlassian 帳號不隸屬於任何單一產品——在 Jira 移除離職人員的存取權後，帳號依然存在、依然可登入，且可能仍持有其他站台的權限。未經 Guard 納管，就無法強制其改用公司 IdP 登入，也無法在 IdP 停用時連動解除全部存取權。

什麼是服務帳號？

服務帳號（service account）代表應用程式或自動化流程，而非真人使用者。與個人建立的 API token 不同，服務帳號不隸屬於任何員工，該人員離職時不會連帶失效；其權限範圍與使用情形亦可由管理員集中檢視與撤銷。常見用途為 CI/CD（Continuous Integration／Continuous Delivery）流程、系統整合與排程工作。詳見 Atlassian 官方說明。

重點能力說明

對照表中幾項需要進一步理解的機制

對照表以單行呈現各項能力，但其中六項的實際運作方式會直接影響導入工作量與選版判斷。

Premium

資料分級與自動分類

Guard Premium 於組織層級提供 Public、Internal、Confidential、Restricted 四級標籤，套用對象為 Confluence 頁面與 Jira 議題。標籤本身不具強制力：將頁面標為 Restricted 不會自動封鎖任何操作，必須另行建立「以分類等級為條件的組織級政策」，該等級才會實際限制分享與匯出行為。

自動分類則於內容寫入時比對敏感樣式，命中信用卡號等格式即自動套用對應等級，用以降低仰賴人工標記所產生的落差。導入順序通常為先以手動分級建立少量高價值內容的基準，再逐步開啟自動分類。初期誤判比例過高時，標籤的可信度會連帶受影響。

Standard · Premium

資料安全政策

可限制匯出、公開分享連結、匿名存取與第三方應用程式的資料存取，兩種方案均具備。差別在於套用條件：Standard 以空間或專案為範圍，屬一體適用；Premium 則可將分類等級作為條件，例如「Confidential 以上一律封鎖對外分享連結，Internal 以下不受限」。

此項為兩方案的主要分野。若安全要求可以「整個空間全開或全關」表達，Standard 即可滿足；若必須依內容本身的敏感程度採取不同管制，才需要 Premium 的分級能力。

Premium

內容掃描與自訂偵測規則

內容掃描提供 60 項以上內建偵測，涵蓋個人資料、金融資訊、憑證與健康資料，並以兩種模式運作：全站掃描對既有內容執行一次性盤點，即時掃描則於內容寫入當下判定。

內建偵測以國際通用格式為主（信用卡號、雲端服務金鑰、美國社會安全號碼等）。台灣的身分證字號、健保卡號與統一編號不在預設清單內，須以自訂偵測規則建立。此項工作量需納入導入時程評估。另有兩項涵蓋限制：掃描不執行光學文字辨識，亦不涵蓋附件內容；以掃描檔形式流通文件的組織，實際覆蓋率會低於偵測項目數所呈現的水準。

Standard · Premium

稽核記錄的兩個層次

兩者的記錄對象不同：Standard 記錄管理員的操作行為，Premium 另涵蓋使用者對內容的檢視與匯出行為。

兩者各自涵蓋哪些操作、保留多久，逐項對照見本節下方。

Premium

告警、調查與修復動作

可疑活動偵測涵蓋異常登入、大量匯出與資料外洩徵兆，命中後於統一的調查儀表板呈現，包含行為者脈絡與事件時間軸，免去跨多個管理介面拼湊事件經過。告警可送達 Slack 或 Microsoft Teams，稽核記錄亦可經 Webhook 與 API 串流至 Splunk 等資安事件管理平台。儀表板並提供可直接執行的修復動作：停用帳號、遮蔽敏感內容、重新分類。

告警機制的效果取決於收斂程度，而非偵測規則的數量。上線前需設定告警等級與接收對象，並訂定高風險項目的處理時限。未經分級的情況下，未處理告警的累積會使儀表板失去判讀價值。

資料分類四級

四個等級分別對應什麼內容，又實際限制了什麼

資料分類為 Guard Premium 與 Standard 之間最明確的差異所在；惟等級名稱本身不具效力，實際限制須由資料安全政策賦予。等級的數量與名稱可由組織自行定義，本節以 Atlassian 預設的四級架構說明。

Level 1

Public

已確認可對外揭露的內容，不含任何未公開資訊。

典型內容
對外發布的產品說明、公開技術文件、行銷素材、徵才資訊、已發布的新聞稿。
套用政策後
允許匿名檢視與公開分享連結，匯出與第三方應用程式存取均不受限。此為唯一預期會以公開連結流通的等級。
容易忽略的一點
未分類的內容不等於 Public。未帶標籤的頁面不會被視為公開，但同樣不受任何分級政策約束——這是導入初期覆蓋率必須先行盤點的原因。
Level 2

Internal

限組織成員檢視的日常工作內容，多數頁面與議題屬此級。

典型內容
專案規劃、會議記錄、內部流程與教育訓練文件、一般開發議題與技術討論。
套用政策後
封鎖對外公開分享連結與匿名存取；組織內部成員的檢視、編輯與匯出行為不受限制。
容易忽略的一點
此級適合作為導入初期的基準等級：先以 Internal 涵蓋大多數內容，再往上分出少量高敏感內容，比一開始就建立細緻的分級規則更容易維持。
Level 3

Confidential

外流將造成商業或法遵損害，僅限特定團隊或角色接觸。

典型內容
報價與定價策略、合約條款、客戶名單、財務數據、尚未公布的產品規劃、個人資料檔案。
套用政策後
於 Internal 的限制之外，另禁止匯出（PDF、Word、CSV 等格式）與第三方應用程式讀取內容。
容易忽略的一點
此級是自動分類的主要落點：內容掃描命中信用卡號、雲端服務金鑰等樣式時會自動升級至此。台灣的身分證字號、健保卡號與統一編號不在內建的 60 餘項偵測清單內，須自行建立自訂偵測規則，此工作量應納入導入時程。
Level 4

Restricted

僅限最小必要範圍存取，任何一次未授權檢視都須留下記錄。

典型內容
系統憑證與 API 金鑰、法務與併購文件、人事調查資料、資安事件記錄、受監理規範約束的客戶資料。
套用政策後
於 Confidential 的限制之外，另禁止外部協作者存取，並可將內容排除於 Rovo 等 AI 助理的檢索範圍。命中偵測規則時觸發告警，並於調查儀表板提供建議修復動作：停用帳號、遮蔽敏感內容、重新分類。
容易忽略的一點
分類標籤依附於內容本身，而非其所在的 Space 或專案。標為 Restricted 的文件無論被移至何處，均受同一套政策約束——這正是分級相對於空間權限設定的主要價值。

適用說明：一、分類標籤本身不具強制效力，上述限制須於組織層級另行建立「以分類等級為條件的資料安全政策」，方能生效。二、此處列舉之限制為常見的政策設定範例，並非產品預設值，實際行為以組織所建立的政策為準。三、分級式資料政策為 Guard Premium 專屬；Guard Standard 的資料安全政策以空間或專案為套用單位，於其範圍內一體適用。相關差異詳見功能對照表；政策如何選定範圍與疊加，見下一節資料安全政策。

資料安全政策

讓標籤產生實際限制：一組政策 ＝ 範圍 × 規則

分類標籤只是內容上的註記，實際限制由組織層級的資料安全政策執行。一組政策只有兩個要件：管到哪些資料（覆蓋範圍）與不允許做什麼（規則）；名稱、描述、建立者與啟用狀態則是一般的管理欄位。政策建立於組織層級，同一組規則可跨 Jira 與 Confluence 一致執行，單一組織最多可建立 50 組。

以下以一組名為 Finance data 的政策為例。財務團隊的預算表與稽核底稿分散在 Jira 議題與 Confluence 頁面，管理者不想逐一空間設定，於是把範圍定為兩個產品的全部內容，規則只挑兩項：禁止匯出、禁止建立公開連結（圖四）。

圖四：Finance data 生效後，Jira 與 Confluence 內的任何頁面或議題都無法匯出為 PDF、Word 或 CSV，也無法產生公開分享連結；未勾選的「匿名存取」與「應用程式存取」則不受此政策影響。範圍決定「管到哪些資料」，規則決定「不允許做什麼」——下方分別說明範圍的三種選法，以及多組政策同時涵蓋同一內容時的效果。

常見問題

導入前最常被提出的問題

導入與功能範圍
導入 Guard 之前需要完成哪些前置作業？

Guard Standard 有兩項前置作業：網域驗證（domain verification）與使用者認領（user claim）。組織須先證明擁有該電子郵件網域，方能將使用該網域的 Atlassian 帳號納為受管帳號，後續的單一登入、驗證政策與稽核機制才會生效。此步驟需與 IT 或 DNS 管理者協調，其所需時間會影響整體導入時程。

哪些訂閱已內含 Guard Standard？

Cloud Enterprise 訂閱內含 Guard Standard。此外，Teamwork Collection 的 Premium 與 Enterprise 方案亦內含 Guard Standard，Standard 方案則不包含。已透過上述任一訂閱取得 Guard Standard 的組織，若後續要升級 Guard Premium，僅需補足每位使用者的價差，無須重複購買 Standard。

免費版的使用者是否也會計入費用？

會。只要帳號位於受 Guard 管理的網域，並持有 Jira、JSM、Confluence、Bitbucket、Trello 或 Statuspage（含免費版）的存取權，即計入 Guard Standard 帳單。若確認部分帳號無須納管，可建立非計費政策將其排除。惟須留意，這些帳號同時也不再受 Standard 的功能保護，且在 Premium 的計費中仍會被計入。

Premium 為何僅支援 Jira 與 Confluence？

Premium 的核心能力為內容掃描與資料分級，目前的偵測引擎涵蓋 Jira 與 Confluence Cloud。Bitbucket、Trello 與 Statuspage 仍在 Standard 的身分與存取控制範圍內，但不受內容掃描涵蓋。若組織的敏感資料主要存放於程式碼儲存庫，須另行評估補強方案。

資料外洩防護的偵測範圍有哪些已知限制？

內容掃描目前針對頁面與議題的文字內容，有三項已知的涵蓋限制：不執行光學文字辨識、不涵蓋附件檔案內容，且尚未支援 Confluence Whiteboard。以掃描檔或附件形式流通敏感資料的組織，實際覆蓋率會低於偵測項目數所呈現的水準，此差距須於概念驗證階段實測確認。

取消訂閱後會產生哪些影響？

強制單一登入與強制兩步驟驗證將失效，使用者改以 Atlassian 帳號登入，部分人員可能需重設密碼；內容掃描與行為偵測停止運作，告警不再送出。已驗證的網域不受影響，仍可繼續檢視與管理受管帳號，部分關鍵設定會保留一段期間。退款僅限月繳試用後的第一個付費月份內，或年繳付款後 30 日內提出。

是否可以先行試用？

可以。兩種方案均提供 30 天免費試用，由組織管理員於 admin.atlassian.com 啟用。試用期間可選定兩至三個代表性的 Space 或專案執行全站掃描，以實際命中結果驗證偵測規則與組織資料型態的符合程度。

使用者與計費
受管使用者、計費使用者與外部使用者如何區分？

受管使用者（managed users）指帳號位於已驗證網域、因而受組織控管的帳號；計費使用者（billable users）則是實際計入帳單的人數。兩者不必然相等：受管帳號若未持有任何受支援產品的存取權，就不會計費；反之，非受管網域的外部協作者只要具備受支援產品的存取權，仍會計入 Standard 帳單。實際人數可於 admin.atlassian.com 的帳單預估頁面查看。報價應以該數字為準；以組織通訊錄人數推估通常與實際計費人數有落差。

Premium 的計費人數如何認定？與 Standard 有何不同？

兩者的計費基礎並不相同。Standard 計入具備 Jira、JSM（Agent）、Confluence、Bitbucket、Trello 或 Statuspage 存取權的使用者；Premium 則僅計入具備 Jira 或 Confluence 存取權者，且不分方案版本。已停用的帳號、未持有任何產品存取權者，以及僅使用 JSM 或 Jira Product Discovery 的使用者，不計入 Premium。因此在同一組織中，Premium 的計費人數通常低於 Standard，估算升級成本時，直接以 Standard 的人數乘以價差會高估實際金額。

JSM 的報修者會計入費用嗎？

不會。僅透過客戶入口網站（portal-only）提交或追蹤案件的帳號，不計入 Guard Standard 帳單；實際處理案件的 JSM Agent 才會計費，且該 Agent 須使用受管帳號。對於以 JSM 作為全公司 IT 服務台、報修者動輒數百至數千人的組織，此項差異對總成本的影響幅度大，估算時須區分 Agent 與報修者的人數。

人數成長時帳單會如何變動？會事先通知嗎？

Guard 依當期實際計費人數計算，人數增加時帳單隨之提高。若當期金額高於前一期，帳務與技術聯絡人會在扣款前三日收到通知信；但這是扣款前的告知，而非事前核准機制。人數波動較大的組織可於 admin.atlassian.com 的訂閱管理頁面定期檢視使用量。將「新進人員取得產品存取權」納入既有的帳號開通流程，可避免帳單在未經察覺的情況下逐月增加。
